## Active backend

- Source entry point: `backend/src/server.ts`
- Application composition and routes: `backend/src/api/app.ts`

## Sibyl configuration

- Production adapter: `backend/src/memory/sibyl-memory-adapter.ts`.
- Service boundary: `backend/src/memory/memory-service.ts`.
- Official transport: `@modelcontextprotocol/sdk` stdio client launching `SIBYL_MCP_COMMAND` (default `sibyl-memory-mcp`).
- Docker pins official `sibyl-memory-mcp==0.1.13` in a Python virtual environment.
- Required production flag: `MEMORY_ENABLED=true`; production configuration rejects `false`.
- Optional persistent path: `SIBYL_MEMORY_DB`; Compose maps it to `/data/sibyl/memory.db` on the `continuity_sibyl` volume.
- Optional Sibyl credentials: `SIBYL_CREDENTIALS`; values are neither required for the local MCP database proof nor logged by application code.
- Current calls include search/recall, remember, event recording, and state setting.
- Current limitation: `MemoryService` returns the Continuity memory ID but does not expose the provider record/event IDs needed for the requested machine-verifiable Phase 28 evidence.
- Current demo uses two separately invoked Node processes and the production adapter, but controlled simulated agents/deliverables. It lacks a single orchestrator, git hash, consolidated JSON artifact, provider event identifiers, and strict process/run assertions.

## Virtuals configuration

- SDK: `@virtuals-protocol/acp-node-v2@0.1.12`.
- Production adapter: `backend/src/integrations/virtuals/virtuals-acp-adapter.ts`.
- Execution and persistence: `backend/src/integrations/virtuals/virtuals-execution-service.ts` and `virtuals-job-repository.ts`.
- Implemented SDK calls include `AcpAgent`, `PrivyAlchemyEvmProviderAdapter`, `browseAgents`, `createJobByOfferingName`, `getSession`, `getApi().getJob`, `session.fund()`, `session.complete()`, and `session.reject()`.

## Base configuration

- Adapter: `backend/src/integrations/base/base-viem-adapter.ts`, using `viem@2.55.19`.
- Service and persistence: `base-payment-service.ts` and `base-transaction-repository.ts`.
- Networks: Base Sepolia default; Base mainnet exists behind explicit `BASE_ALLOW_MAINNET=true`.
- Assets: native ETH and configured ERC-20/USDC.
- Controls implemented: fixed recipient validation, maximum amount, mission budget, asset validation, idempotency key, transaction persistence, confirmation/revert/uncertain handling, and bearer operator token.
- Configuration currently uses `BASE_NETWORK`, not the requested explicit `BASE_CHAIN_ID` contract.
- **Not live verified:** no repository evidence contains a genuine transaction hash, receipt, and explorer confirmation.
- Product-semantics gap: the current action is named/described as an agent payment, which can look like duplicate payment beside ACP funding. It must become a distinct post-verification mission-level action before any live transaction.

2. The Sibyl proof is not yet the requested one-command, self-validating, cross-process evidence package and does not expose official provider record/event IDs.
3. The five PostgreSQL integration tests are skipped; migrations and durable constraints are not yet demonstrated against disposable PostgreSQL in this baseline.
4. Virtuals is implemented but not live verified; no real job/funding/deliverable/settlement receipt exists.
5. Virtuals offering capabilities are over-assigned from mission requirements instead of established from offering metadata.
6. Virtuals post-restart `JobSession` reconstruction support is unresolved.
7. Base is implemented but not live verified; no real hash/receipt/explorer evidence exists.
8. Base currently represents an agent payment rather than a clearly distinct post-verification mission-level action.
9. Mission execution is synchronous in HTTP requests; no production background worker, startup recovery, or autonomous reconciliation exists.
10. Recovery planning and ledgers exist, but production does not scan and resume non-terminal missions on startup.
11. No explicit durable state machines cover every requested Virtuals and Base external boundary.
12. No public-deployment manifest, public URL, readiness endpoint, or Render persistent-disk proof exists.
13. Public mission execution and operational data are not sufficiently protected for an Internet-facing deployment; rate limiting is absent.
14. The dashboard does not yet present the requested judge-first causal timeline from runtime evidence.
15. No authoritative live end-to-end receipt exists.
16. No production restart/recovery demonstration exists.
17. No public GitHub URL, signed-out deployment, demo-video URL, Base explorer evidence, Virtuals evidence URL, build-log post, or demo post is available.
